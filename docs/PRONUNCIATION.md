# Pronunciation-robust understanding (G-039 / W1)

Status: **implemented and gated in CI**. Target: intent accuracy >= 0.92 and
false-answer rate < 0.03 on >= 150 accent-degraded utterances. Owner: W1
(task-8). Branch: `feat-4`. No commits made by W1.

## Headline numbers (192 utterances, 4 accent profiles)

| Path | Intent accuracy | False-answer rate |
|---|---|---|
| BEFORE (rescue/repair/gate disabled) | **53.65%** | **46.35%** |
| AFTER (pronunciation layer on) | **96.88%** | **0.00%** |
| Target | >= 92% | < 3% |

False-answer = the gate said "answer" but the recovered question matched a
different hand-labeled intent. BEFORE is the legacy behaviour (degraded ASR text
goes straight to the detector and is always answered confidently).

### Gate + rescue + repair (AFTER)

- Gate: 92 answered / 70 hedged / 30 clarified. Nothing ambiguous is answered
  confidently.
- Rescue: 121 spans / 196 tokens (114 variant, 4 homophone-context, 3 phonetic).
- Repair pass: 113 calls (only segments that still had non-high-confidence
  words), 18 ms simulated provider latency, max 18 ms, 100% inside the 150 ms
  budget. In this corpus rescue already fixes every garbled entity, so the
  repair applier confirmed 0 additional span edits - its positive path is proven
  by unit tests (`pronunciation.test.ts`), where "bostgres" -> "PostgreSQL" is
  applied and a suggestion that touches a high-confidence word is rejected.
- Hard rule: 192/192 utterances checked, **0** high-confidence tokens mutated.

### Demo hook for `make demo`

The pipeline accepts an opt-in option and does not change the default demo:

```ts
import {
  isDemoPronunciationEnabled,
  createDemoPronunciationStage,
  demoPronunciationPipelineOptions,
} from "@/features/pronunciation";

const pronunciation = isDemoPronunciationEnabled() // DEMO_PRONUNCIATION=1
  ? demoPronunciationPipelineOptions(createDemoPronunciationStage())
  : undefined;

await runDemoPipeline({ ...existingOptions, pronunciation });
```

With the flag on, the demo emits `pronunciation.understanding` events
(`decision`, `confidence`, `corrections`, `repairElapsedMs`,
`answerLanguage`, `codeSwitched`) and suppresses the answer when the gate asks
for a clarification. `runDemoPronunciationStage("Is Kubernetes overkill for a monolith?",
{ profile: "east_asian" })` prints/returns the degraded text, recovered text,
gate decision and clarification/hedge sentence for a manual demo.

## Hard rules (asserted)

1. **Never touch high-confidence tokens.** `HIGH_CONFIDENCE_THRESHOLD = 0.82`;
   rescue never rewrites a high-confidence token (or a span containing one), and
   the repair applier rejects such suggestions. The metrics gate checks all 192
   utterances (0 violations); the unit tests assert both layers directly.
2. **Never confidently answer the wrong question.** Below the gate threshold
   (segment confidence 0.78) the gate returns hedge/clarify; with two competing
   canonical readings it returns the "heard: X - did you mean Y?" clarification.
3. **Rescue only against the vocabulary.** No free-form spelling edits; every
   replacement comes from the session vocabulary / domain phoneme map.
4. **Repair is budgeted.** 150 ms wall clock; timeout/failure falls back to
   rescue-only output.
5. **Named entities are preserved.** Unverified entity edits are rejected.
6. **Answer language never switches.** The code-switch detector reports
   primary/secondary hints but `answerLanguage` is always the session language.

## Limitations

- The accent profiles are deterministic *models* of accent-conditioned ASR
  errors (term substitution + confidence model), not recorded audio and not a
  hosted ASR. The corpus therefore measures the rescue/repair/gate logic, not a
  real provider's WER. Real-provider WER remains uncovered (G-038).
- BEFORE keeps the repo's existing `stt-normalizer` table. The corpus
  deliberately stresses confusions that table does not cover (new company/person
  names and unseen jargon), which is why BEFORE drops to 53.65%.
- Intent matching is a hand-authored keyword-group matcher (16 intents), not a
  trained semantic classifier; accuracy is intent-class hit rate, not answer
  quality.
- The repair pass is a fallback: in this corpus rescue resolves every garbled
  entity first, so the repair applier made no additional edits (it still ran on
  113 low-confidence segments inside budget). Real LLM latency exceeds 150 ms,
  so a production provider must be a fast small model or run best-effort off the
  critical path; the seam and hard rules are in place either way.
- Homophones that phonetics cannot separate (cache/cash) are resolved only with
  context cues; otherwise the gate clarifies. A clarification can pick a
  stopword as the "heard" token when the degraded content word is unknown - it
  fails safe (asks) but reads awkwardly.
- The demo runner's live ASR path does not yet request keyword boosting/n-best
  from Deepgram by default; the contract and adapter parameters are ready and
  tested, but wiring the session's vocabulary into the production listen call is
  a follow-up integration (demo pipeline behind `DEMO_PRONUNCIATION=1` is wired).
