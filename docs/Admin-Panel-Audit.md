# HireShade Admin Panel Audit — Mini-Phase ADMIN-M0

**Status:** Read-only audit. No application code modified. No database modified. No migration executed. No commits made.

**Scope:** Map the entire admin panel (`admin/`) against the current, live HireShade schema (`lib/db/src/schema/index.ts`) and identify every mismatch before any database migration work starts.

**Method:** Static inspection only — reading `admin/app/pages/**/{page.json,api.server.ts,index.tsx}` (34 pages), `admin/app/_server/**`, `admin/app/lib/auth.ts`, `admin/app/components/RBACGuard.tsx`, and `lib/db/src/schema/index.ts`. No database connection was made and no admin server was started or rebuilt for this audit.

### B.3 — Naming-convention mismatch pattern

- Admin tables: PascalCase, e.g. `"User"`, `"Session"`, `"CreditPurchase"`, `"AssistantChat"`.
- Admin columns (seen throughout `page.json` `config.columns`): camelCase, e.g. `createdAt`, `userId`, `durationSeconds`, `creditExhaustedAt`, `disconnectedAt`, `lastHeartbeatAt`, `clerkId`, `uploadedAt`.
- Live schema tables: snake_case, e.g. `users`, `sessions`, `credits_purchases`, `assistant_chats`.
- Live schema columns: snake_case, e.g. `created_at`, `user_id`, `clerk_user_id`.
- Postgres table/column identifiers are case-sensitive when quoted; every admin query quotes them (knex default), so `"User"` and `users` are genuinely different relations, not a casing artifact.
- Example concrete column drift: `session/page.json` config expects `creditExhaustedAt`, `disconnectedAt`, `startedAt`, `lastHeartbeatAt` on the `Session` table — **none of these fields exist on the live `sessionsTable`** (`lib/db/src/schema/index.ts:93-147`, which has `startedAt`/`endedAt`/`updatedAt` but no `creditExhaustedAt`, `disconnectedAt`, or `lastHeartbeatAt`).
- Example: `users/page.json` expects column `clerkId`; live schema column is `clerk_user_id` (`lib/db/src/schema/index.ts:54`).

## C. Broken/stale pages

1. **`management`** (`admin/app/pages/management/page.json:13-15` declares `allowInsert: true, allowUpdate: true, allowDelete: true`, but `admin/app/pages/management/api.server.ts` implements only `customDataFetcher`, `getUserResumes`, `getUserSessions`, `getResumeDetails`, `getSessionDetails` — zero create/update/delete procedures). Config/implementation mismatch: the UI is told mutation is allowed, but there is nothing behind it. Whether clicking a mutate action errors cleanly or does something unexpected was **not verified** in this pass (would require running the admin UI, out of scope for a read-only audit).
2. Every page bound to a PascalCase legacy table (24 pages) is reading against tables absent from the live schema. Best case: the query errors ("relation does not exist"). Worst case: if legacy ScribeShade tables still physically exist in the same database (not ruled out), the page silently displays old data that looks current, with no visual indicator that it's stale. **Which of these two outcomes actually occurs is UNKNOWN — requires direct database introspection (`\dt` or equivalent), which was out of scope for this read-only, no-DB-access audit.**
3. `atsAnalytics`, `sessionAnalytics`, `usersAnalytics` all query non-existent live tables (`"ATSAnalysis"`, `"Session"`, `"User"`) inside `WITH daily_stats AS (...)` / `cumulative AS (...)` CTEs (`admin/app/pages/atsAnalytics/api.server.ts:33`, `admin/app/pages/sessionAnalytics/api.server.ts`, `admin/app/pages/usersAnalytics/api.server.ts`) — these dashboard/chart pages would show empty results or SQL errors against the live DB (caught and logged, not surfaced as a hard crash — each wraps its query in `try/catch` returning `[]` on error, per `atsAnalytics/api.server.ts:63-67`).

## E. Transcript visibility gaps

**Confirmed: transcripts cannot currently be viewed from admin.**

- Live transcripts and AI answers both live in one table, `session_messages` (`id, session_id, role, content, question, answer, current_version, ai_model, source, created_at, updated_at` — `lib/db/src/schema/index.ts:155-177`). `role` values used in practice: `"USER"`, `"INTERVIEWER"`, `"AI_ASSISTANT"` (confirmed from `artifacts/api-server/src/routes/sessions.ts:667-672` and `:1457`).
- No admin page binds to `session_messages` (confirmed against the full 33-page table-binding list in Section B.2 — absent).
- The only transcript-shaped page, `transcriptChunk` → `"TranscriptChunk"`, does not even conceptually match a transcript. Its `page.json` columns are: `id, endTime, startTime, createdAt, userId, difficulty, question, questionGroupId, questionId, sessionId, technologies`. This is a **question-bank chunking table** — `difficulty` and `technologies` are exactly the shape of the live `questions` table's own columns (`lib/db/src/schema/index.ts:335-355`), not transcript speech content. There is no `content`/`text`/`role`/`speaker` column anywhere in this page's config. So even under the old ScribeShade schema, `transcriptChunk` was never a "what was said" viewer.
- **Conclusion: there is no admin page, old or new, that has ever exposed transcript text (interviewer or candidate speech) in this codebase as it currently stands.**

## F. Credits/payment visibility gaps

- **Read-side:** `creditPurchase`, `creditUsage`, `creditLedger`, `userCreditBalance`, `billing`, `creditPack`, `creditConfig`, `featureCost` all target tables absent from the live schema (Section B.2) — no confirmed visibility into real purchases, usage, or balances as they exist today.
- **Write-side — highest-severity finding in this audit:** `grantCredits` → `assignCredit` procedure (`admin/app/pages/grantCredits/api.server.ts:61-130`) is a **fully implemented, transactional credit mutation**:
  ```ts
  // admin/app/pages/grantCredits/api.server.ts:71-121 (abridged)
  return await db.transaction(async (trx) => {
    let balance = await trx('UserCreditBalance').where('userId', userId).forUpdate().first();
    // ... computes newEarnedCredits / newTotalAvailable ...
    await trx('UserCreditBalance').where('userId', userId).update({ earnedCredits: newEarnedCredits, totalAvailable: newTotalAvailable, lastUpdated: new Date() });
    // or .insert(...) if no balance row exists
    await trx('CreditLedger').insert({ id: ledgerEntryId, userId, type: 'EARN', amount, balanceBefore, balanceAfter: newTotalAvailable, reason: 'Manual credit grant by Admin', createdAt: new Date() });
    return { success: true, newEarnedCredits: ..., newTotalAvailable: ..., ledgerEntryId };
  });
  ```
  This is real, working, row-locked (`forUpdate()`), transactional write code — but it targets `"UserCreditBalance"` and `"CreditLedger"`, **neither of which exists in the live schema.** The live app's balance-check logic (`getAvailableCredits`, referenced in `artifacts/api-server/src/routes/sessions.ts:23` from `artifacts/api-server/src/lib/sessionCredits.ts`) reads from `credits_balance`, a completely different table.
  **Consequence: if an admin uses "Grant Credits" today, the call succeeds and returns a plausible-looking success response (`{ success: true, newEarnedCredits, newTotalAvailable, ledgerEntryId }`), but the user's real, live balance in `credits_balance` never changes.** This is a silent no-op from the end user's perspective, and gives the admin operator false confidence that a support case was resolved.

## G. Auth/security risks

1. **Admin identity storage is broken/ephemeral.** `admin/app/_server/app.ts:51-64`:
   ```ts
   const identityProvider = createIdentityProvider('sqlite', {
     fileName: ':memory:', // replaced below — no sqlite file is ever written to disk
     passwordHashAlgorithm: 'bcrypt',
     jwtSecretSalt: process.env.JWT_SECRET_SALT,
     rootUsername: process.env.ROOT_USERNAME,
     rootPassword: process.env.ROOT_PASSWORD,
   });
   // Swap the internal sqlite knex instance with a Postgres one.
   //(identityProvider as any).db = buildPgDb();
   ```
   A `buildPgDb()` helper (`app.ts:12-49`) exists specifically to back the identity provider with a durable, dedicated `kottster_auth` Postgres schema — but the line that wires it in is **commented out**. The identity provider is left on `fileName: ':memory:'`. Any non-root admin account created through Kottster's own user-management UI exists only in memory and is **lost on every server restart**. The only durable login path is the single shared root credential pair (`ROOT_USERNAME`/`ROOT_PASSWORD` env vars, checked directly, never touching the DB) — meaning no individual admin accountability, no per-user audit trail, no way to revoke one admin's access without rotating the shared root password for everyone.

2. **RBAC "is admin" check is a broad heuristic**, `admin/app/lib/auth.ts:22-36`:
   ```ts
   const isAdministrative =
       Boolean(userAsAny.isAdmin) === true ||
       Boolean(userAsAny.is_admin) === true ||
       username === 'admin' ||
       email.includes('admin@') ||
       userRoles.includes('superadmin') ||
       userRoles.includes('admin');
   ```
   `email.includes('admin@')` is a substring match, not an exact-domain check — an email like `notadmin@example.com` or `xxxadmin@evil.com` would satisfy it. Combined with finding 1 (no durable, verifiable identity store for non-root users), this heuristic — rather than a real role table — is the practical gatekeeper for full admin bypass of every page's `allowedRoles` restriction.

3. **Default-allow when `allowedRoles` is empty.** `admin/app/lib/auth.ts:38-57` (`hasAccessToPage`):
   ```ts
   const allowedRoles: string[] = config?.allowedRoles || [];
   if (allowedRoles.length === 0) return true;
   ```
   Any authenticated user gets access to a page with no `allowedRoles` declared. In this audit, all 34 pages had at least one role listed in `page.json` (Section A/B), so this default was not observed to be triggered in practice — but it is a live default worth knowing before adding new pages in ADMIN-M1.

4. **Declared-but-unimplemented mutation flags** — `management` and (less severely, since its backend genuinely implements the mutation) `grantCredits` both declare `allowInsert/Update/Delete: true` in `page.json`. Whether the corresponding `index.tsx` UI presents a confirmation dialog before firing a mutating call was **not verified** in this pass (would require reading each page's React component and/or exercising the running UI, both out of scope for static/read-only audit).

5. **Enforcement layer is unclear.** `RBACGuard` (`admin/app/components/RBACGuard.tsx`) enforces role checks at the **React route level** only. Whether Kottster's own procedure-dispatch layer (inside the `@kottster/server`/`@kottster/react` framework packages, not this repo's code) independently re-checks `allowedRoles`/permissions when a procedure like `assignCredit` is invoked directly (bypassing the page route), or relies solely on the client-side guard, is **UNKNOWN** — verifying this would require reading the Kottster framework's internal source, which was not done in this pass.

## H. Pages safe to keep

- **`quickLinks`** — fully self-contained, backed by its own local SQLite file (`app.db`, `admin/app/pages/quickLinks/api.server.ts:6-19`), entirely unrelated to the HireShade/ScribeShade Postgres schema. Its `createLink`/`updateLink`/`deleteLink` CRUD is correctly wired against its own isolated data with basic input validation (non-empty title/URL). Low risk; functionally sound as-is; irrelevant to the migration question.
- The routing/RBAC scaffolding itself (`main.tsx` auto-discovery, `RBACGuard`, per-page `page.json` config format) is reasonable, reusable infrastructure. The problem identified throughout this audit is entirely in *what each page is bound to*, not in the framework wiring.

## I. Pages needing rewrite (before any migration validation can be trusted)

Priority order:

1. **`grantCredits`** — highest priority. Currently performs a real, transactional write to dead tables while returning a false-success response. Must be fixed or fully gated off before any admin uses it again.
2. **A new transcript/`session_messages` viewer** — does not exist at all today (Section D/E). Required before migration validation can confirm transcripts and AI answers survived the move, which is the stated purpose of this whole ADMIN-M0/M1 workstream.
3. **`users`, `session`, `resume`, `document`, `project`/`projectVersion`, `assistantChat`/`assistantMessage`, `sessionFeedback`** — repoint `page.json` `config.table`/column names to the live snake_case equivalents (`users`, `sessions`, `resumes`, `documents`, `projects`/`project_versions`, `assistant_chats`/`assistant_messages`, `session_feedback`). These are the core entities needed for spot-checking during migration.
4. **`creditPurchase`, `creditUsage`, `userCreditBalance`** — repoint to `credits_purchases`, `credits_usage`, `credits_balance`; needed specifically to validate the credits migration.
5. **`management`** — either implement the declared mutation procedures properly, or remove the `allowInsert/Update/Delete: true` flags so the UI stops advertising a capability that doesn't exist server-side.
6. **Lower priority / candidates to drop entirely** (old-schema-only concepts with no confirmed live equivalent — a product decision is needed on whether these still exist in HireShade before rebuilding them): `company`, `policy`, `resumeTemplates`, `builtResume`, `sessionNotes`, `qA`, `askAiMessage`, `answerGenerationSnapshot`, `idempotencyKey`, `creditLedger`, `creditConfig`, `creditPack`, `featureCost`, `atsAnalytics`.

## J. Smallest Mini-Phase ADMIN-M1 implementation plan

Scoped to exactly what's needed to make the admin panel trustworthy enough to validate the future migration — nothing more:

1. **Close the false-success credit grant.** Gate `grantCredits` to no role (or set `hideInSidebar: true` and remove all `allowedRoles`, effectively disabling it) until it is repointed at `credits_balance`/`credits_usage`. Zero new code — a config-only change.
2. **Repoint the 6-7 core read-only pages** (`users`, `session`, `resume`, `document`, `sessionFeedback`, `creditPurchase`, `creditUsage`, `userCreditBalance`) to the live snake_case tables/columns. Same Kottster `databaseTable` fetch strategy already in use — only `page.json` `config.table` and `config.columns[].column` values need correcting. No new controller logic.
3. **Add one new read-only page for `session_messages`**, filterable by `session_id`, displaying `role`, `content`, `question`, `answer`, `source`, `created_at`. This is the single missing piece needed to visually confirm a migrated session's transcript and AI answers, and to distinguish `USER`/`INTERVIEWER`/`AI_ASSISTANT` rows via the `role` column.
4. **Leave everything else untouched** for this mini-phase (`company`, `policy`, `qA`, `atsAnalytics`, etc.) — none of it blocks migration validation; revisit after a product decision on which old-schema concepts still apply to HireShade.

This is a plan only. Nothing in this list has been implemented as part of this audit.

## Explicit blockers before database migration can be validated through admin

1. `grantCredits` must be disabled or fixed — it is a live, working write path to tables the migration will not touch, and will keep silently failing to reflect real balances regardless of migration outcome.
2. No page exists to inspect `session_messages` — migration cannot be visually validated for transcript/AI-answer integrity without one.
3. All core entity pages (`users`, `session`, `resume`, `document`, credits trio) must be repointed to live table/column names — otherwise post-migration spot-checks through the admin UI will show errors or stale/empty data regardless of whether the migration itself succeeded.
4. The admin identity provider's in-memory/non-persistent configuration should be resolved (or at minimum understood and accepted) before relying on multiple admin operators to validate migration results — currently only the shared root account is a durable login.
5. Database introspection (an explicit `\dt`/schema dump against both the admin's target DB and `artifacts/api-server`'s target DB) is needed to close the "Unknowns" in Section K before any migration mapping can be finalized with confidence.
